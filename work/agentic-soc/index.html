System shape

02

Problem

#

The goal was to remove repetitive work while keeping consequential decisions with a person. An autonomous SOC was never the target. Python and PowerShell jobs handled deterministic tasks, while LLM workflows used Model Context Protocol servers on a read-only Splunk role. Human approval remained required before agent actions that could change state.

03

Engineering decisions

#
DecisionWhyTradeoff / boundary
Give the agent read-only Splunk accessEnrichment and investigation benefit from broad search context without granting write authority.Read-only access still requires data-scoping and prompt-injection awareness.
Use MCP as a capability boundaryExpose explicit tools instead of giving an LLM arbitrary system access.Tool schemas reduce freedom but make behavior easier to review and constrain.
Require human approval before writesKeep accountability for consequential actions with an analyst.Approval adds friction, which is acceptable when the alternative is unbounded automation.
Use scripts for deterministic workPython and PowerShell are preferable when the task has a stable, testable path.LLMs should not replace simpler automation merely because they are available.

Sanitized reconstruction

The artifact is a public control model, not a production authorization export. It makes the intended boundaries reviewable: read-only evidence access, narrow tools, explicit denied capabilities, and human approval before state change.

Regression cases

  • Read-only enrichment succeeds without granting a state-changing tool.
  • Permission or tool failures stop the workflow instead of falling back to a broader capability.
  • Model interpretation stays distinguishable from retrieved security evidence.
  • Any proposed state change remains visible to and approved by a human analyst.

05

Validation

#

Validation focuses on boundary behavior as much as task completion. Can the agent perform the intended read-only enrichment? Does it fail closed when a tool or permission is unavailable? Are proposed actions visible to a person before execution? Can the analyst distinguish retrieved evidence from model-generated interpretation?

06

Failure modes I care about

#
  • Prompt content attempts to redirect the agent outside the intended task.
  • The model overstates confidence and an analyst treats generated interpretation as evidence.
  • A tool exposes more capability than the workflow requires.
  • The workflow silently falls back to an unsafe path when a dependency fails.
07

What I would improve next

#

Add adversarial prompt-injection fixtures and explicit provenance labels on every retrieved datum so the workflow can be regression-tested against over-trust and instruction hijacking.

08

Questions I get asked

#
Is this an autonomous SOC?

No. The design intentionally keeps the agent in a bounded support role. Read-only context and human approval are features, not temporary limitations.

Why MCP?

It creates a clean contract between the model and security tools. Instead of arbitrary access, the workflow gets named capabilities with explicit inputs and outputs.

Where should an LLM not be used?

Deterministic tasks with stable logic are usually better as normal code. LLMs are useful where language, summarization, or flexible reasoning adds value, not as a default automation engine.

What is the biggest risk?

Over-trust. A polished answer can look more certain than the evidence supports, so the workflow must preserve source context and keep consequential decisions with the analyst.
