01

System shape

#
02

Problem

#

The problem was alert volume without enough context. Roughly 300 per-event alerts a day made it harder to separate routine noise from activity that deserved investigation, and related behaviors were being reviewed as isolated events instead of as part of the same story.

The redesign moved lower-confidence behaviors into risk accumulation rather than alerting on each event. Each behavior contributes risk against a user or system, ATT&CK context helps explain why it matters, and a smaller set of risk incident rules escalate accumulated risk. Daily alerts fell from roughly 300 to 75 with coverage retained.

03

Engineering decisions

#
DecisionWhyTradeoff / boundary
Aggregate risk instead of escalating every eventReduce duplicate analyst work and preserve context across related behaviors.Requires disciplined modifiers and risk-incident logic so accumulation does not become opaque.
Annotate risk behavior with ATT&CK contextGive analysts a consistent semantic layer for why behavior matters.ATT&CK mapping is context, not proof that a technique occurred.
Keep a known-positive regression pathGive rule changes a repeatable way to test the expected escalation path.Known-positive tests cover known scenarios, not unknown future attacks.
Keep triage logic close to the detectionMake the next analyst action obvious when a risk incident fires.Too much enrichment can hide the core reason the alert exists.
04

Implementation evidence

#
SPLRepresentative risk-rule output shape
/*
  Representative SPL shape for a risk-rule output: the contribution half
  of risk-based alerting. Sanitized reconstruction. Not production
  configuration. Rows produced here become scored risk events;
  rba-risk-incident.spl shows how they are aggregated.
*/
| tstats summariesonly=t count
    min(_time) as first_seen max(_time) as last_seen
  from datamodel=Authentication.Authentication
  where Authentication.action="failure"
  by Authentication.user Authentication.src
| rename Authentication.* as *
| eval risk_object=user,
       risk_object_type="user",
       risk_score=case(count>=20,40,count>=10,20,true(),0)
| where risk_score>0
| eval risk_message="Repeated authentication failures from source=".src
| table first_seen last_seen risk_object risk_object_type
        risk_score risk_message count
Sanitized reconstruction

This is a sanitized reconstruction showing normalization, risk-object construction, scoring, and analyst-facing context. It is not a production correlation search or threshold export.

Regression cases

  • A known-positive replay or representative fixture reaches the expected escalation path.
  • A single weak behavior does not become an analyst-facing incident by itself.
  • Missing telemetry becomes a feed-health failure, not evidence of a clean environment.
  • Underlying behaviors remain visible enough for the analyst to explain why risk accumulated.

SPLRepresentative risk incident rule
/*
  Representative risk incident rule: the aggregation half of risk-based
  alerting. Sanitized reconstruction; thresholds are illustrative, not
  production values.

  Risk rules (see rba-representative.spl) write scored risk events per
  object into the Risk data model. This clean-room example watches the
  accumulated picture per object and raises one notable when the score
  crosses an illustrative threshold. ATT&CK annotations remain useful
  analyst context but are not asserted here as a production trigger.
*/
| tstats summariesonly=true
    sum(All_Risk.calculated_risk_score) as risk_score
    values(All_Risk.annotations.mitre_attack.mitre_tactic_id) as tactics
    values(All_Risk.annotations.mitre_attack.mitre_technique_id)
        as techniques
    dc(source) as contributing_rules
    values(All_Risk.risk_message) as risk_messages
    min(_time) as first_seen max(_time) as last_seen
    from datamodel=Risk.All_Risk
    where All_Risk.risk_object_type IN ("user", "system") earliest=-24h
    by All_Risk.risk_object All_Risk.risk_object_type
| rename All_Risk.* as *
| where risk_score >= 100
| eval trigger="score_threshold"
| table risk_object risk_object_type risk_score contributing_rules
        trigger tactics techniques risk_messages first_seen last_seen

/*
  Production-specific thresholds, throttling, weighting, contribution
  caps, and escalation details are intentionally not represented here.
*/
The other half

The risk rule above contributes. This rule decides. It reads the risk index rather than raw telemetry, sums score per object, and escalates when the accumulated score crosses the representative threshold.

Regression cases

  • Each known-positive regression case reaches the expected score-based escalation path.
  • A noisy contributor is visible in the contributing-rule output so it can be tuned at the source.
  • Risk observations older than the window fall out of the sum, so stale risk does not accumulate forever.
  • The output names the contributing rules, so the analyst can see which behavior drove the escalation.

05

Validation

#

The public result I can support is straightforward: daily alert volume fell from roughly 300 to 75 and coverage was retained. I do not publish employer validation data. For a redesign like this, my validation standard is a maintained known-positive replay or representative fixture set that exercises the escalation path before older logic is retired.

Alert volume is only one part of the result. The stronger follow-up measures are per-incident-rule precision, analyst disposition, and whether the regression set still exercises the behaviors the detection is supposed to catch.

THE TRADE

The tradeoff is lower sensitivity at the individual-rule alert level. Weak behaviors stop paging an analyst on their own, but they remain collected, scored, and available as part of the accumulated risk context. The measurement standard page sets out the questions I would ask about this number and what I would measure alongside it.

06

Failure modes I care about

#
  • Risk scores drift upward until almost everything becomes high risk.
  • A risk incident rule aggregates unrelated activity and produces context without meaning.
  • A source stops feeding, so the absence of detections looks like a clean environment.
  • Analysts cannot tell which underlying behavior caused escalation.
  • Silent decay: a source changes format, the risk rule keeps running and returns nothing, and that behavior quietly stops contributing while the rule still reports as healthy.
  • The regression set stops being maintained, so new known-positive scenarios never join it and coverage ages out.
07

What I would improve next

#

If I were doing the redesign again, I would instrument per-detection precision and analyst disposition before changing the alerting model. I would also make the known-positive regression set an automated gate on rule changes.

08

Questions I get asked

#
Why not just tune the noisy correlation searches?

Tuning individual searches can help, but risk aggregation changes the decision model. It lets lower-confidence behaviors contribute context without requiring every event to become an analyst-facing alert.

How do you defend the coverage claim?

The supported result is that coverage was retained. I do not publish employer validation data. The public standard shows the regression method I expect for this kind of change: known-positive replay or representative fixtures, plus boundary and missing-data tests.

What metric would you add next?

Per-detection precision over time, analyst disposition, and the ratio of risk incidents to confirmed incidents. Those metrics make tuning a continuous feedback loop.

Was 300 alerts a day a healthy baseline?

No. The original model was already too noisy. I do not treat the whole reduction as proof that the redesign was better; the useful checks are whether coverage stayed intact, whether the remaining incidents carried better context, and whether analysts could work them more effectively.

What is the main RBA failure mode?

Opaque scoring. If an analyst cannot explain why risk accumulated or which behavior matters, the model becomes harder to trust even if alert counts fall.
