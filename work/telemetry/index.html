02

Problem

#

Security analytics is only as dependable as its data path. Work in this area included onboarding more than 30 data sources to CIM with custom field extractions and parsers, then later building three production Technology Add-ons in Python and onboarding identity, CSPM, firewall, and proxy telemetry with feed-health alerting.

03

Engineering decisions

#
DecisionWhyTradeoff / boundary
Normalize to CIM before scaling detectionsReusable fields and data models reduce one-off SPL and make correlation logic portable across sources.CIM mapping can hide source-specific nuance if original fields are discarded too aggressively.
Treat feed health as a security controlA silent data source can create a false sense of safety. Health needs its own alert path.Health alerts must distinguish expected maintenance from real collection failure.
Build production TAs when vendor collection is insufficientOwn parsing, checkpoints, API behavior, and field quality when out-of-box collection does not meet the need.Custom code creates maintenance responsibility and version-compatibility work.
Validate at collection, parsing, and semantic layersA feed can be arriving while still being unusable for detections.More validation adds operational cost, so checks need to be targeted.
04

Implementation evidence

#
SPLRepresentative feed-health control
/*
  Representative feed-health pattern. Sanitized reconstruction, not
  production configuration.

  Design: the durable inventory of expected feeds is kept separate from
  the recent-event health window, so a feed that has never reported is
  distinguished from one that stopped.
  Shape: tstats for what actually arrived, inputlookup append=t for what
  should have, then one stats to reconcile. No join: a subsearch join is
  bounded by subsearch limits and re-runs the inner search; append plus
  stats scales with the number of feeds.
*/
| tstats latest(_time) as last_seen count as events
    where index=* earliest=-7d
    by index sourcetype
| eval observed=1
| inputlookup append=t expected_security_feeds
| stats max(last_seen) as last_seen sum(events) as events
        max(observed) as observed
        values(expected_interval_sec) as expected_interval_sec
        values(owner) as owner values(criticality) as criticality
    by index sourcetype
| eval age_sec = now() - last_seen
| eval health = case(
      isnull(expected_interval_sec),       "UNEXPECTED",
      isnull(observed),                    "MISSING",
      age_sec > expected_interval_sec * 2, "SILENT",
      age_sec > expected_interval_sec,     "LATE",
      true(),                              "HEALTHY")
| where health != "HEALTHY"
| table index sourcetype owner criticality last_seen age_sec events
        health
Sanitized reconstruction

The public query separates durable expected-feed inventory from recent health state. Production indexes, sourcetypes, intervals, and owners are intentionally absent.

Regression cases

  • Expected feed with no recent events becomes MISSING rather than disappearing from the denominator.
  • Late data is distinguishable from zero-volume data.
  • Collection success is checked separately from field and CIM semantic quality.
  • A schema change that preserves ingest but breaks required fields is treated as a data-quality failure.

05

Validation

#

Validation is layered: confirm events arrive, confirm timestamps and sourcetypes are correct, confirm required fields extract, confirm CIM mappings populate, and confirm downstream searches return expected results. Feed-health alerting watches the collection path separately from detection logic.

VISIBILITY VS COVERAGE

A detection that queries a source nobody is ingesting still counts as coverage on a heatmap. That is why feed health is treated here as part of detection engineering: visibility (is the telemetry arriving, at usable quality) is measured separately from coverage (does a detection exist), because they fail independently. The measurement standard sets out the four columns I report instead of one percentage.

06

Failure modes I care about

#
  • Events arrive but timestamps are wrong, moving them outside detection windows.
  • A vendor schema changes and field extractions fail without stopping ingest.
  • Duplicate collection inflates volume and changes statistical baselines.
  • CIM fields populate incorrectly, so accelerated data-model searches return misleading results.
  • A feed stops and nothing notices, because absence of events looks the same as absence of attacks.
07

What I would improve next

#

Add contract-style semantic tests per critical source so required fields, types, cardinality bounds, and CIM mappings can fail before detection behavior drifts.

08

Questions I get asked

#
What makes onboarding complete?

Not just ingest. I want correct time, stable sourcetype, useful fields, CIM where appropriate, volume sanity, health monitoring, and a consumer query that proves the data is usable.

When would you not force CIM?

When the source has important semantics that do not map cleanly. Keep original fields and normalize the common security concepts without flattening away useful detail.

Why custom Technology Add-ons?

When reliable API collection, checkpointing, parsing, or normalization is not available out of the box, a maintained TA gives the team explicit control over the ingestion contract.

How do you detect a silent feed?

Track last-seen time and expected volume against a durable inventory or baseline. Absence needs to be evaluated separately from detection results.
